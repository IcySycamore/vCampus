# 应用层协议规定（v1 草案）

> 状态：**草案，待确认**
> 范围：客户端与服务器端之间基于 TCP 的 `Message` 通信约定
> 关联：`docs/adr/0006`（通信协议与线程模型）、`CONTEXT.md`（术语）

---

## 1. 概述

本协议规定客户端与服务器端**如何通信**，是两端及网络（Server 端 / Client 端 / 协议）共同遵循的唯一约定。

- **传输层**：TCP 长连接（一个客户端一条连接，会话期内保持）。
- **应用层**：Java 对象序列化，传输统一的 `Message` 信封。
- **两端共享**：`vcampus-common` 中同一份类定义，保证序列化一致。

---

## 2. 传输基础

| 项 | 约定 |
| --- | --- |
| 传输协议 | TCP |
| 连接模型 | 每客户端一线程，服务端线程池管理 |
| 消息流 | `MessageStream`（封装收发 `Message` 的对象流） |
| 消息载体 | `edu.seu.vcampus.common.message.Message` |

---

## 3. 包结构（Message 信封）

所有通信内容都装在 `Message` 信封里，字段如下：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| uid | `Long` | 消息唯一标识 |
| command | `int` | 命令码（标识要执行的操作，见 §4） |
| statusCode | `String` | 状态码 |
| data | `Object` | 传输数据（任意可序列化对象） |
| sender | `String` | 发送者用户名 |

> 命令标识采用数字命令码字段 `command`（见 §4）。

## 6. 通信流程

### 6.1 连接建立与线程分配

服务端：

1. `ServerSocket serverSocket = new ServerSocket(port)` 绑定监听端口。
2. 进入监听循环：`while (running) { Socket socket = serverSocket.accept(); ... }`，其中 `accept()` 阻塞等待连接。
3. accept 返回 `Socket` 后，服务端从线程池 `ClientThreadMan` 取出一个**空闲线程**，把「socket + 随后建好的消息流」交给这个线程。
4. 该线程负责这条连接的**整个会话**：初始化消息流 → 登录 → 请求/响应循环 → 断开清理。

客户端：

1. `Socket socket = new Socket(host, port)` 向服务器发起 TCP 连接。
2. 连接建立后，两端各自持有一个 `Socket` 对象，代表这条连接。

### 6.2 消息流初始化（⚠️ 防死锁，两端必须相反）

两端各自创建 `MessageStream`，用它封装收发 `Message` 所需的输入流 / 输出流。其内部初始化顺序两端**相反**：

- **服务端**的 `MessageStream`：先创建输出流，再创建输入流。
- **客户端**的 `MessageStream`：先创建输入流，再创建输出流。

- 原因：输入流构造时会读取并验证 stream header，两端若都先建输入流，会互相等待对方写 header → 死锁。
- `MessageStream.writeMessage` 内部每次写完都要 `flush()`，否则数据可能滞留在缓冲区不发送。

### 6.3 登录（连接 ≠ 登录）

1. 客户端构造登录请求 `Message`：`command` 填登录命令码（如 `101`），`data` 填用户名 / 密码，`sender` 填用户名，然后 `writeMessage` 发出。
2. 服务端 `recvMessage` 收到，交给用户管理模块校验账号密码。
3. 校验通过：服务端在该连接的会话对象里**记录登录身份**（uid、角色），此后该连接发出的所有请求都视为该用户操作。
4. 服务端返回响应 `Message`：`statusCode` 填 `200`（成功）或 `401`（失败）。
5. 客户端 `recvMessage` 收到响应，检查 `statusCode`，决定进入主界面或提示登录失败。

### 6.4 请求 / 响应循环（会话主循环）

服务端（每个连接对应的 `ClientThread` 内）循环执行：

1. `Message req = stream.recvMessage();` 阻塞等待客户端请求。
2. 若为心跳消息 → 直接回心跳响应，回到第 1 步。
3. 按 `req` 的命令码 `command` 分发到对应模块的 Service。
4. Service 处理业务，返回结果对象。
5. 构造响应 `Message`：`statusCode` 填结果状态，`data` 填业务结果。
6. `stream.writeMessage(resp);` 写回客户端。
7. 回到第 1 步继续等待下一条请求。

客户端一次交互：

1. 构造请求 `Message`（命令码 + 参数放 `data`），`writeMessage` 发出。
2. `Message resp = stream.recvMessage();` 阻塞等待响应。
3. 读 `resp.statusCode` 判断成功与否，读 `resp.data` 获取结果，刷新界面。

约定：**一次交互 = 一条请求 + 一条响应**，由服务端处理线程内同步完成，同一连接不并发写。

### 6.5 心跳

- 客户端每隔固定时间（如 5 秒）发一条心跳 `Message`。
- 服务端收到心跳，记录该连接的「最后活跃时间」，并回一条心跳响应。
- 服务端检查：超过阈值（如 15 秒）未收到任何消息 → 判定客户端已断线，走断开流程。
- 目的：检测「客户端直接关窗口 / 断网」这类没有正常登出的异常断开。

### 6.6 断开

四类触发条件：

1. 客户端主动登出 / 断开（正常）；
2. 心跳超时（见 6.5）；
3. 读超时 / EOF：`recvMessage` 抛 `EOFException` 或读超时（客户端异常断开）；
4. 服务器主动停机。

断开后的统一清理步骤：`stream.close()`（内部关闭对象流与 socket）→ 线程归还线程池。

## 7. 序列化约定

**序列化**：把内存中的 Java 对象转换成可在网络传输、可存磁盘的字节流；**反序列化**：把字节流还原成对象。本协议用 Java 对象序列化传输 `Message`。

规则：

- `Message` 及 `data` 中装载的**所有对象**，以及这些对象内部嵌套引用的对象，都必须 `implements Serializable`，否则 `writeMessage` 时会抛 `NotSerializableException`。
- `Serializable` 是**标记接口**：没有任何方法，只是告诉 JVM「这个类可以被序列化」。
- 每个可序列化类带 `private static final long serialVersionUID = 1L;`：
  - 它是类的**序列化版本号**，用来校验「发送方与接收方的类定义是否一致」；
  - 两端版本号不一致 → 反序列化抛 `InvalidClassException`；
  - 协议变更（增删字段）时，要同步更新它并全组周知。
- 两端类定义必须**完全一致**（共享 `vcampus-common` 同一份类）：类名、包名、字段名与类型都要一致，否则反序列化失败。
- `data` 字段只放业务实体或简单数据（`String`、`Integer`、实体对象等），**不放不可序列化对象**（如 `Socket`、`Connection`、`Thread`）。
- 某个字段不想被序列化时，加 `transient` 关键字：序列化会跳过它，接收端还原后该字段为默认值（如 `null` / `0`）。

---

## 8. 异常与断开处理（服务端网络实现要点）

- 捕获 `EOFException`：客户端异常断开，走会话关闭流程。
- 读超时：socket 设 `setSoTimeout`，超时未收到数据判定断开。
- 心跳：客户端周期性发心跳命令码，服务端超时未收到即回收线程与连接。
- 所有断开路径统一：调 `stream.close()`（关流 + 关 socket）→ 归还线程，避免资源泄漏。
