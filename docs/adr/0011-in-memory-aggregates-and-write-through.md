# 内存态聚合：三处 DAO 为什么整表装进内存，以及为什么本轮不动

本 ADR 记录 vCampus 服务端「把整张表读进内存、变更写穿到库」这一形态的**现状与承重理由**。
起因是有人问：「通用数据库层没有查询支持吗？搞得还要全量读出」。结论是：**有查询能力，
但这三处的全量加载都在承重，不能按「顺手优化」处理**。本 ADR 给出证据、改造方案与顺序，
并明确本轮（feat/db-migration，验收前）**不改**。

**Status**: accepted

**Context**:

服务端有两类持久化形态并存：

1. **按需查询**（多数）：`JdbcUserRepository`、`StudentDaoJdbc.findByUserUuid`、图书馆四个
   `*DaoJdbc`（带 `WHERE` 与 `LIMIT/OFFSET`）等，每次业务动作只取需要的那几行。
2. **内存态聚合 + 写穿**（三处）：构造时整表载入 `ConcurrentHashMap`，之后每次变更先改内存、
   再写库。分别是 `BankService`、`CourseDao`、`ScoreDao`。

通用层的边界要说清楚：`server/db/DbHelper` 只提供连接配置与 `getConnection()`／`requireAvailable()`，
`server/db/JdbcSupport` 只提供连接生命周期、`closeQuietly`／`blank`、可空参数绑定与
`inTransaction`（事务唯一入口）。**没有查询构造、没有行映射器、没有条件下推、也没有缓存层** ——
所以「按需查」的 SQL 与列映射成本必须由每个 DAO 自己付。第 2 类形态正是这种成本下的选择。

**Decision**:

## D1 三处全量加载的现状与承重用途

| 位置               | 启动时载入                                                                                      | 承重用途（不只是为了省事）                                                                                                                                                                             |
| ------------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `BankService` 构造 | `loadAccounts()` 全表，逐账户 `loadCredential()` + `loadTransactions()`，再 `loadMaxSequence()` | `BankRecord.verifyPayment` **靠内存流水做支付幂等**：扫 `transactions` 找同 `relatedOrderId` 的 `CONSUMPTION` 记录，金额不符即拒；`page()` 分页、余额一致性也都在同一把 `synchronized (record)` 下完成 |
| `CourseDao` 构造   | 学院 / 教师 / 选课学生 / 教室 / 课程 5 张表全量（课程带选课名单、时间槽、可选专业子表）         | 选课匹配（可选专业、教师方向要求）、时间冲突检测、学院↔教师双向索引都在内存里算；子表写入是「先删后插」的整体替换语义                                                                                  |
| `ScoreDao` 构造    | `loadAll()` 全量成绩                                                                            | 仅按学生/课程查、按学期 upsert；三处里**最没有承重理由**的一处，属跟随前两处的写法                                                                                                                     |

另有一处**半全量**：`StudentService.listStudents` 先 `m_dao.findAll()` 取全量，再补姓名 → 过滤 →
排序 → 切片（`PageSlice`）。原因写在方法注释里：查询条件是「按姓名搜」，而姓名不在学籍表，
是联查用户模块算出来的，没法直接下推。

## D2 为什么「顺手改成懒加载」会出事

- **银行**：`verifyPayment` 是支付去重的唯一防线。启动不预载流水，重启后它扫不到历史消费记录，
  同一订单会被**重复扣款**；`page()` 也会退化成只能看到本次启动之后的流水。要改必须把幂等判定
  下推成 SQL（`WHERE btRelatedOrderId = ?`）并加唯一约束兜底，那是**语义变更**，不是优化。
- **课程**：把匹配/冲突/双向索引从内存搬到 SQL 是一次重写；`CourseStore` 的注释已经写明
  「改造它的成本远高于换掉存储」。
- **学籍列表**：真正缺的是 `StudentDao` 上没有「带条件 + 分页」的查询方法。姓名已经在
  `tblUserCredential.ucName`，一次 `JOIN` + `LIMIT` 就能只取一页，接口形状不变。

## D3 没有关机回写，风险在别处

`VCampusServerApp.registerShutdownHook()` 只做两件事：停止监听、关闭线程池。三处都是**写穿**
（每次变更先改内存再落库），所以不存在「关机时把内存写回库」的路径。真正的风险是
**内存已改、写库失败**时的两边不一致 —— 这是写穿形态的固有问题，与是否懒加载无关。

## D4 本轮不改，改造按此顺序

本分支（`feat/db-migration`）**不动这三处**：三处都在承重、当前无一例功能缺陷（722 个测试全绿），
而验收在即，改动收益是架构整洁、代价是可能打断验收链路。改造优先级与顺序（若后续排期）：

1. `ScoreDao` → 按需查：新增「按学生/按课程」查询方法，`ScoreService` 与 `CourseMessageHandler`
   调用点同步；回归面最小。
2. `StudentService.listStudents` → 下推：`StudentDao` 增带条件分页方法，SQL 内 `JOIN tblUserCredential`
   取姓名，`StudentMatcher`／`StudentSorter`／`PageSlice` 退化为「已下推时不再需要」或删除。
3. `BankService` 流水 → 先下推幂等判定（`relatedOrderId` + 唯一约束），**再**谈懒加载；
   顺序反了会重复扣款。
4. `CourseDao` → 最后，且要先决定「匹配/冲突算在内存还是 SQL」，属设计变更。

**Consequences**:

- 好处：把「为什么全表装内存」和「改了会怎样」写进仓库，避免后续把这三处当随手可优化项，
  尤其避免有人在没下推幂等判定前就把银行流水改成懒加载。
- 代价：三处内存占用随数据量线性增长（流水最明显），单机部署下可接受，多实例部署前必须改造。
- 通用层保持只做连接与事务：不引入查询构造器／缓存层，避免再造一个「看环境决定行为」的中间层。
