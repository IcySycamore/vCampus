# 单条消息上限与批量分片；客户端状态缓存归属；心跳与判活职责

一次围绕「心跳是否有效 / 超时后会发生什么 / 批量导入会不会拖垮链路」的评审，暴露了三类问题：批量命令没有体积上限、
展示数据被塞进认证契约、以及断线后界面无反馈。本 ADR 固化评审结论。

**Status**: accepted

**Considered Options**（详见 `docs/本次重构实施清单.md` 的决策记录）

- 服务端把业务处理搬出读循环（每连接 worker）：**不采纳**——前提是「不存在巨型包/慢 handler」，而该前提由 D1 保证。
- 客户端「连续 4 次心跳无 ACK 即判线重连」：**不采纳**——真断线时服务端 15s 先断、客户端立刻收到 FIN；ACK 判线只对「网络黑洞」提前约 10s，却会把「服务端忙」误判成「服务端死」。
- 用「会话 30 分钟过期」来断开连接：**不采纳**——连接回收（TCP 层空闲）与会话有效期（业务层身份）是两个正交概念，合并会让沉默用户白占连接 30 分钟。

**Decision**:

## D1 单条消息有上限；批量一律分片

- 列表类查询**一律分页**：`PageResponse`，单页 ≤ 100 条（`PageResponse.MAX_PAGE_SIZE`）。
- 批量命令**单次 ≤ 50 条**：新增 `common.constant.ProtocolLimit.MAX_BATCH_SIZE = 50`，**双端共用同一常量**
  （客户端切片与服务端校验不可能不一致）；服务端超限回 `400`。
- **客户端负责分片**：`UserService.batchRegister(list, listener)` 在 API 层内部按 50 切片、逐片发送、
  聚合成一个总 `BatchResult`；1000 条 = 20 个包。界面只调一次，并通过进度回调显示「已导入 150 / 1000」
  ——**不允许静默分片**（否则用户以为卡死）。

## D2 因此不做「服务端处理解耦」与「ACK 判线重连」

D1 保证单条消息毫秒级 ⇒ 无慢 handler、无写阻塞 ⇒ 读循环不会被业务长期占用。这两项改造**明确不做**。

> **复议记录（2026-09-13）**：PR #34 提出 `ServerBusinessExecutor`（把 handler 移出读循环），触发场景是
> 「学籍列表联查姓名」。该场景与 D1 同源——列表走分页、批量走分片，单条 handler 就不会长期占用读循环；
> 因此仍不采纳。若将来出现「单条请求本身就要秒级」的功能（跨库事务、大文件），须回到本 ADR 重新评估。

## D3 心跳：保留双向，客户端消费 ACK 但不作为判线依据

- 客户端 5s 发心跳（`ClientHeartbeat`，独立守护线程），服务端收到即回 `HEARTBEAT_ACK`，并刷新 15s 空闲计时。
- 服务端 `soTimeout = 15000` **保留**：它负责回收「客户端被 kill / 网线拔掉（无 FIN）」的僵尸连接。
- 客户端**消费 ACK**（不再丢弃），但不据此判线，用途是观测 RTT 与时间同步。
- 真断线的发现路径：服务端 15s 断开 → 客户端收到 FIN → 立即感知；兜底是客户端 30s 读超时。
- **断线一律回登录页**（见 ADR-0009 D9）：不允许再出现「连接没了、界面还在、点什么都失败」。

## D4 时间同步搭载心跳 ACK

- 心跳请求携带客户端发送时刻，ACK 回显该时刻并附服务端时刻；客户端用**最小 RTT 采样 + 单调递推**估计 offset。
- 时间同步**只用于显示与时间戳对齐**；会话有效期、防重放等安全判定**一律服务端权威**（客户端时钟不可信）。

## D5 批量写语义

`UserRepository` 增加 `saveAll(...)`（语义：一批一次落盘）。文件版据此把 N 次全量重写降为 1 次；
MySQL 版对应「一个事务 / 批量 insert」——同一抽象，两种实现都正确。

## D6 展示数据随会话下发，不再单独拉档案

- 姓名等展示字段**随登录会话一次性下发**（`SessionEntry.m_display_name`，由 PR #35 落地并已合并）：
  客户端直接用会话里的姓名，不再为「显示我的名字」多打一次请求。
- 客户端仍**不把展示数据落盘**：会话只存内存，随登出/断线丢弃（`ClientSession`）。
- 若将来展示字段变多（头像、部门…），再引入独立的 `UserProfile` DTO 与查询命令，而不是继续往会话里塞。

## D7 姓名存账户层（与课程表结构一致）

- 姓名存 **`tblUser.uName`**，对应 `common.user.entity.User.mDisplayName`；**档案表不放姓名**
  （`tblStudentRecord` 本就没有 name 列）。
- 依据：课程给定的建库脚本 `sql/vCampus.sql` 中 `tblUser` 已有 `uName VARCHAR(20) NOT NULL COMMENT '姓名'`，
  而「姓名只在人员档案」需要给课程给定的表加列，成本与风险都更高。
- 服务端保证**姓名非空**：未采集时用登录名顶上，因此界面不会出现空白；管理员没有姓名概念，天然走这条。

**Consequences**

- `103` 已在处理器里校验条数与 `MAX_BATCH_SIZE`（超限回 400），客户端批量导入按 50 分片并显示进度。
- 姓名以 `tblUser.uName` 为准；账户层已有承载位（`User`/`Credential`/管理员引导文件的姓名列）。
- 断线一律回登录页已实现（`SessionLifecycle`：登出与断线共用一个收口点，且带防重入）。
- 将来要做「服务端主动推送」时，再引入「连接注册表 + 订阅/退订 + 重连重订阅」——本 ADR 不涉及，
  且届时优先用真实需求（审核结果、订单状态）驱动。
