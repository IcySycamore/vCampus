## 1. 结论先行（TL;DR）

三条铁律：

1. **数据库**：绝不存明文密码，也不存裸的 `sha256(密码)`，要存**加盐哈希** `sha256(salt + 密码)`。
2. **传输**：网络上绝不传明文密码，也**不直接传** `sha256(密码)`，要传**挑战-应答**算出来的一次性结果。
3. **会话**：登录成功后服务器签发一个随机 `token`，之后**每条消息都带 token**，服务器只认 token、不认客户端自己填的用户名。

---

## 2. 基础概念（不懂的先看这里）

| 词 | 一句话解释 | 能反推回原文吗 |
| --- | --- | --- |
| 明文 | 用户敲的原始密码，比如 `abc123` | —— |
| 哈希（Hash） | 把任意内容压成固定长度的一串十六进制，比如 `sha256("abc123")` | **不能**（单向，不可逆） |
| 盐（Salt） | 每个用户一段**随机**字符串，和密码拼在一起再哈希，防「彩虹表」 | 盐本身不是秘密 |
| 挑战码（Nonce） | 服务器临时生成的一次性随机数，防「重放攻击」 | 一次性，用完即废 |
| Token | 登录成功后发的「临时通行证」，之后靠它证明身份 | 服务器里能查到对应的人 |

**哈希最重要的两条性质**（一定要理解）：

- **不可逆**：知道哈希值算不回原文，所以库泄露了也拿不到明文。
- **同样的输入 → 同样的输出**：所以验证时只要「重算一遍，再比对」，不必知道原文。

## 3. 密码存储：加盐哈希

### 3.1 为什么不能存明文

数据库一旦泄露，所有用户的真实密码直接暴露；而且很多人多个网站用同一个密码，等于一次泄露全部家当。

### 3.2 为什么不能存裸的 `sha256(密码)`

- **彩虹表**：攻击者预先算好「常见密码 → 哈希」的大表，库泄露后直接查表反推出常见密码。
- **同密码同哈希**：两个用户都设 `abc123`，库里哈希一模一样，一眼看穿。

### 3.3 加盐怎么做

> **盐由谁生成、何时生成**：salt 由**服务器端**在**用户注册时**生成——每个用户一个、随机、落库后永久固定，登录时不再重新生成；客户端在注册阶段不接触 salt，只有登录第 2 步服务器才临时下发（见 §4.4）。

每个用户注册时：

1. 生成一段**随机盐** `salt`（建议 16 字节，用 `SecureRandom`）；
2. 计算 `H = sha256(salt + 密码)`；
3. 数据库里存两样东西：`salt` 和 `H`（分开两列，或合并成 `salt$H` 一列）。

验证密码时：

1. 取出该用户的 `salt`；
2. 算 `sha256(salt + 用户刚输入的密码)`；
3. 和库里存的 `H` 比对，相等即密码正确。

> **关键认知：盐不是秘密**。它的作用只是让「同密码的两个用户哈希不同」并废掉彩虹表，所以盐可以被任何人看到，甚至可以随挑战码下发给客户端（见 §4.4）。

### 3.4 Java 代码：算 SHA-256

所有组员共用这一个工具方法即可（放在 `vcampus-common` 里）：

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;

public final class HashUtil {

    private HashUtil() {
    }

    /** 计算字符串的 SHA-256 十六进制摘要（64 位小写十六进制）。 */
    public static String sha256Hex(String input) {
        try {
            MessageDigest md = MessageDigest.getInstance("SHA-256");
            byte[] bytes = md.digest(input.getBytes(StandardCharsets.UTF_8));
            StringBuilder sb = new StringBuilder();
            for (byte b : bytes) {
                // 注意 b & 0xff：把 byte 转成 0~255 的无符号值，避免出现 ffffff 前缀
                sb.append(String.format("%02x", b & 0xff));
            }
            return sb.toString();
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException("当前环境不支持 SHA-256", e);
        }
    }
}
```

生成随机盐和 token 也共用一组工具方法：

```java
import java.security.SecureRandom;

public final class RandomUtil {

    private static final SecureRandom RANDOM = new SecureRandom();

    private RandomUtil() {
    }

    /** 生成 n 字节随机数，转成十六进制字符串（长度 2*n）。 */
    public static String randomHex(int bytes) {
        byte[] buf = new byte[bytes];
        RANDOM.nextBytes(buf);
        StringBuilder sb = new StringBuilder();
        for (byte b : buf) {
            sb.append(String.format("%02x", b & 0xff));
        }
        return sb.toString();
    }
}
```

- 盐：`RandomUtil.randomHex(16)` → 32 位十六进制；
- token：`RandomUtil.randomHex(16)` → 32 位十六进制（用安全随机源，不可预测）。

## 4. 登录：挑战-应答（详细流程）

### 4.1 为什么不能直接传 `sha256(密码)`

组长的原始想法是「客户端把 `sha256(明文)` 传上去，服务器再 `sha256` 一次存库」。

**问题**：如果客户端每次发的都是**固定**的 `sha256(密码)`，那这个哈希值在网络里就**等于密码本身**。攻击者截获后，直接把这个固定哈希原样发给服务器就能登录（这叫「传递哈希攻击」/「重放攻击」），服务器再哈希一百次也挡不住——因为攻击者拿到的就是有效凭证。

### 4.2 挑战-应答的核心思想

服务器每次登录先发一个**一次性随机数 nonce**，客户端把 nonce 掺进去再算哈希。因为 nonce 每次不同，所以客户端每次发出去的哈希也不同 → 截获上一次的没法重放。

### 4.3 完整流程（四步）

| 步骤 | 方向 | 消息内容 |
| --- | --- | --- |
| 1 | 客户端 → 服务器 | `LOGIN_REQUEST`：`data` 放 `{username}` |
| 2 | 服务器 → 客户端 | `LOGIN_CHALLENGE`：`data` 放 `{salt, nonce}` |
| 3 | 客户端 → 服务器 | `LOGIN_VERIFY`：`data` 放 `{username, proof}` |
| 4 | 服务器 → 客户端 | `LOGIN_RESULT`：`data` 放 `{token, 用户信息}`（成功）或仅 `statusCode=401`（失败） |

### 4.4 每一步两端各算什么（重点，务必看懂）

先约定三个量：

- `password`：用户输入的明文密码（**只存在于客户端内存，全程不上网、不落库**）。
- `salt`：数据库里该用户的盐（第 2 步服务器下发，见 §3.3）。
- `nonce`：服务器本次生成的一次性随机数（第 2 步下发）。
- 数据库里存的是 `H = sha256(salt + password)`（注册时算好的）。

**第 1 步**：客户端只发用户名，不发任何密码相关的东西。

**第 2 步**：服务器按用户名查库，取出 `salt`，再生成一个 `nonce`（带时效，比如 5 分钟内有效，且一次性），把 `{salt, nonce}` 发给客户端。
> 提示：如果用户名不存在，也返回一个随机的假 salt 和一个 nonce，避免攻击者用「是否有该用户」试探注册情况。

**第 3 步**：客户端本地算：

```
proof = sha256( nonce + sha256( salt + password ) )
```

把 `{username, proof}` 发回服务器。

**第 4 步**：服务器按用户名查库取出 `H`，本地算：

```
expect = sha256( nonce + H )
```

其中 `H = sha256(salt + password)`。然后比对：

- `proof == expect` → 密码正确。生成 `token`，返回成功。
- 不相等 → 密码错误，返回 `401`。

**为什么这两个值相等？** 因为客户端算的 `sha256(salt + password)` 恰好就是库里存的 `H`，两边再用同一个 nonce 套一层 sha256，结果必然一样。**服务器全程不需要知道明文密码**。

### 4.5 nonce 的生命周期（防重放的最后一环）

- 服务器在内存里维护 `nonce → 过期时间` 的映射；
- 每个 nonce **只能用一次**：第 4 步验证完（无论成功失败）立即删除；
- 超过时效（如 5 分钟）还没用，也删除；
- 这样就算有人截获了第 3 步的 `proof`，nonce 已经用过/过期，重放无效。

## 5. 会话 token

### 5.1 为什么需要

登录成功后，客户端还要发很多业务请求（查学籍、选课……）。如果每条请求都重新验证密码，既不现实也不安全。所以登录成功那一刻，服务器发一个 `token` 当「通行证」，之后每条请求带 token 即可。

### 5.2 token 从哪来、怎么用

1. **签发**：登录成功后，服务器用 `RandomUtil.randomHex(16)` 生成一个 token，在服务器内存（或数据库）里记下 `token → 用户ID + 角色 + 过期时间`，并把 token 放进登录响应发给客户端。
2. **携带**：客户端保存 token，之后**每条** `Message` 都填上 `token` 字段（见 §6）。
3. **校验**：服务器（建议在赵芊雅的线程池线程入口统一做）每收到一条消息，先拿 token 查映射：
   - 查得到且没过期 → 放行，并把「真实用户身份」注入当前会话；
   - 查不到 / 过期 → 直接回 `401`，业务代码根本不会执行。
4. **失效**：登出或超时后删除映射，token 作废。

### 5.3 铁律：只认 token，不认客户端自己填的身份

`Message` 里可能有 `uid` / `sender` 之类字段，这些是**客户端自己填的，可以伪造**。所以：

- 访问控制（谁能干什么）**一律以 token 解析出的身份为准**；
- `uid`、`sender` 只用于显示或业务，**绝不**作为鉴权依据。

## 6. Message 信封变更（加 token 字段）

在 `Message` 信封上新增第 6 个字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| uid | `Long` | 消息唯一标识 |
| command | `int` | 命令码 |
| statusCode | `String` | 状态码 |
| data | `Object` | 传输数据 |
| sender | `String` | 发送者用户名（仅供参考，不作鉴权依据） |
| **token** | **`String`** | **会话令牌（登录成功后服务器签发，之后每条请求都带；登录/注册阶段为空）** |

规则：

- 登录请求、注册请求：`token` 为空。
- 登录成功后的**所有**请求：必须带有效 `token`。
- 服务器线程入口：`token` 为空或无效 → 回 `401`，不进入业务。

> 这是 common 模块的公共改动，按 ADR-0007 必须先在此文档与《应用层协议规定.md》中定稿、全组周知，再改代码。

## 7. 命令码建议（用户管理 100–199，供组长定稿）

| 命令码 | 含义 | 备注 |
| --- | --- | --- |
| 101 | 登录请求 LOGIN_REQUEST | 第 1 步 |
| 102 | 登录挑战 LOGIN_CHALLENGE | 第 2 步（服务器下发 salt+nonce） |
| 103 | 登录验证 LOGIN_VERIFY | 第 3 步（客户端回 proof） |
| 110 | 注册 | 注册只需做 §3 加盐哈希，不需要挑战-应答 |
| 120 | 登出 | 服务器删除 token 映射 |
| 130 | 权限/身份查询 | 返回当前 token 对应的身份 |

> 也可用「一个命令码 101 + statusCode 区分阶段」的写法，具体由组长定；本表只是建议。
