# 消息处理接口说明（MessageHandler / MessageDispatcher）

> 状态：**草案，待确认**
> 负责：邬致远（Server 网络 / 学籍模块）
> 关联：`docs/应用层协议规定.md`（命令码 §4）、`docs/adr/0006`（通信协议与线程模型）

---

## 1. 要解决的问题

服务器收到一条 `Message`（例如 `command=201` 查询学籍）后，怎么知道该交给哪个模块、哪个函数处理？

本方案通过「一个接口 + 一个分发器」解决：**根据 command 号段，把消息自动路由到对应模块的处理器**，服务器核心不需要知道每个模块的内部实现。

---

## 1.5 接口清单（各模块负责人该做什么）

| 接口/类 | 位置 | 各模块负责人需要做什么 | 重要度 |
| --- | --- | --- | --- |
| `MessageHandler` | common | **必须实现**：在 `handle` 里写自己模块的业务 | ⭐ 重点 |
| `MessageSender` | common | **只使用**：调 `send(响应)`，不用实现 | 会用即可 |
| `MessageDispatcher` | server | **不用碰**（server 网络组内部使用） | ❌ 不用 |
| `StreamMessageSender` | server | **不用碰**（server 网络组内部实现） | ❌ 不用 |
| `Command` | common | **要填**：自己模块的命令码常量（号段） | 要填号段 |
| `StatusCode` | common | **只使用**：状态码常量 | 会用即可 |

> 一句话：各模块**只需要实现 `MessageHandler`、填 `Command` 号段**；其余（sender、dispatcher、StreamMessageSender）都是 server 网络组的事，各模块只需会用 `sender.send` 发响应即可。

## 2. 三个组件

### 2.1 `MessageHandler` 接口（放 `vcampus-common`）⭐ 各模块必须实现

所有业务模块共用的「处理器契约」，异步式签名：

```java
package edu.seu.vcampus.common.handler;

public interface MessageHandler {
    /** 处理一条请求消息，处理完成后通过 sender 发送响应。 */
    void handle(Message request, MessageSender sender);
}
```

**约定**：

- 入参是请求 `Message`（含 `command` 与 `data`）和一个发送器 `sender`；
- `handle` **不直接返回响应**，而是在处理完成后（可同步、可异步）调 `sender.send(response)` 主动发送；
- 不抛受检异常：业务异常应在实现内部捕获，通过 sender 发送 `500` / `400` 响应。

### 2.2 `MessageSender` 接口（放 `vcampus-common`）—— 各模块只使用、不实现

把「发送响应」的能力交给业务模块，让模块自己决定发送时机：

```java
package edu.seu.vcampus.common.handler;

public interface MessageSender {
    /** 发送一条响应消息。 */
    void send(Message response);
}
```

**为什么用 sender 而不是直接传 MessageStream**：`MessageHandler` 在 common、`MessageStream` 在 server，common 不能依赖 server；sender 接口放 common 解决依赖方向，同时只暴露「发送」能力，不让业务代码触碰连接的其他操作（收消息、关闭等）。

### 2.3 `MessageDispatcher` 分发器（放 `vcampus-server`）❌ 各模块不用碰

维护 `command → MessageHandler` 的映射，提供两个方法：

```java
package edu.seu.vcampus.server.dispatch;

public class MessageDispatcher {
    // 登记：command 与处理器建立映射
    public void register(int command, MessageHandler handler) { ... }

    // 分发：按 command 找到处理器并调用（响应由处理器通过 sender 发）
    public void dispatch(Message request, MessageSender sender) { ... }
}
```

**行为**：

- `register`：启动阶段各模块登记自己负责的命令码；
- `dispatch`：按 `request.getCommand()` 查映射，找到就调 `handler.handle(request, sender)`；**找不到时通过 sender 发 400 响应**。

### 2.4 `StreamMessageSender` 适配器（放 `vcampus-server`）❌ 各模块不用碰

server 端用 `MessageStream` 实现 `MessageSender`，工作线程为每条连接包一个，随请求传给 handler：

```java
public class StreamMessageSender implements MessageSender {
    private final MessageStream stream;
    public void send(Message response) {
        try { stream.writeMessage(response); }
        catch (IOException e) { /* 连接断开，线程池接入后触发清理 */ }
    }
}
```

## 3. 各模块怎么接入（三步）

以「学籍模块」为例：

### 第 1 步：实现 `MessageHandler`

```java
public class StudentMessageHandler implements MessageHandler {
    @Override
    public void handle(Message request, MessageSender sender) {
        switch (request.getCommand()) {
            case Command.STUDENT_QUERY:    // 201 查询学籍
                查询学籍(request, sender);      // 处理完自己 sender.send(响应)
                return;
            case Command.STUDENT_UPDATE:   // 202 提交修改申请
                提交修改(request, sender);
                return;
            default:
                sender.send(错误响应(request));   // 未识别命令回 400
        }
    }
}
```

> 若业务需要异步（如数据库查询慢），可在 handle 里把处理逻辑丢给执行器，处理完再 `sender.send(response)`，不阻塞工作线程。

### 第 2 步：在 `Command` 里登记号段常量（`vcampus-common` 的 `Command.java`）

各模块负责人在完成所属模块时，往 `Command` 里补自己的命令码常量。当前已划分：

| 区段 | 模块 | 负责人 |
| --- | --- | --- |
| 100–199 | 用户管理 | 李文湖 |
| 200–299 | 学籍 | 邬致远 |
| 300–399 | 选课 | 赵芊雅 |
| 400–499 | 图书馆 | 张芸菲 |
| 500–599 | 商店 | 魏雨霏 |
| 600–699 | 银行 | 周奥林 |

### 第 3 步：服务器启动时注册（dispatcher 全局唯一）

`MessageDispatcher` 在服务器启动时 `new` **一次**，各模块把 handler 注册进去；之后这个实例被**所有工作线程共享**：

```java
MessageDispatcher dispatcher = new MessageDispatcher();   // 全局唯一，只 new 一次
dispatcher.register(201, new StudentMessageHandler());
dispatcher.register(202, new StudentMessageHandler());
// ... 其余模块同理
```

注意：上面这段「注册」代码应写在 `VCampusServerApp.main()` 里，在 `listener.start()` 之后、进入 accept 循环之前。注册完成后，运行时只查表（dispatch）、不再 register。

## 4. 工作线程（ClientThread）的职责

服务器的收发循环**不是跑在监听线程里**，而是跑在线程池的**工作线程**里。监听线程只做 accept；accept 到连接后交给工作线程，由工作线程负责这条连接的全部会话。

### 4.1 工作线程的核心循环

```java
// 工作线程内部（简化示意）
MessageSender sender = new StreamMessageSender(stream);   // 包一个发送器
while (连接未断开) {
    Message req = stream.recvMessage();            // ① 收消息（阻塞）
    if (req 是心跳) { 回心跳; continue; }             // ② 心跳处理
    if (需鉴权且 token 无效/过期) { sender.send(401响应); continue; } // ③ token 校验
    dispatcher.dispatch(req, sender);              // ④ 分发（响应由 handler 自己发）
}
stream.close();                                    // ⑤ 断开清理
```

### 4.2 dispatcher 与 sender 在工作线程里的配合

- `MessageDispatcher` 是**全局一个实例**，启动时 `new` 一次，被所有工作线程共享；
- `StreamMessageSender` 是**每连接一个**，由工作线程在会话开始时用 `stream` 包出来；
- 每收到一条消息，工作线程调一次 `dispatcher.dispatch(req, sender)`——查表、未登记回 400 都封装在 `dispatch` 里，业务响应由 handler 通过 sender 主动发。

### 4.3 工作线程还要负责的三件事

1. **心跳超时判定**：客户端每 5 秒发心跳；服务端 15 秒没收到任何消息就判断线、关闭连接；
2. **token 校验**：登录成功后每条消息带 `token`，工作线程入口统一校验，无效/过期回 401；
3. **断开清理**：所有断开路径统一 `stream.close()` 并归还线程。

---

## 5. 边界与注意事项

1. **接口放 common、分发器放 server**：接口要被所有模块实现，所以放 `vcampus-common`；分发是服务端行为，放 `vcampus-server`。
2. **号段不撞车**：各模块只登记自己号段内的 command，不要跨段注册。
3. **线程安全**：`MessageDispatcher` 内部用 `ConcurrentHashMap`，`register` 在启动期单线程完成，`dispatch` 被线程池的多线程并发调用，安全。
4. **未登记 command**：由 dispatcher 通过 sender 发 400（`StatusCode.BAD_REQUEST`），不抛异常、不拖垮连接。
5. **处理器内部异常**：由各模块自己的 `handle` 捕获并通过 sender 发 500 响应，不让异常穿透到网络层。
6. **发送失败**：`StreamMessageSender.send` 内部捕获 IO 异常（连接断开），不向上抛；线程池接入后在此触发连接清理。
