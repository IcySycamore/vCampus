# 学籍模块数据库对接说明

> 状态：**字段已定稿，待 JDBC 实现**
> 负责：邬致远（学籍模块）
> 对接方：数据库设计 / DAO 实现同学
> 关联：`docs/学籍模块接口说明.md`、`docs/adr/0002-database-mysql.md`、`sql/vCampus.sql`

---

## 0. 一句话结论

学籍模块**不新增 VO / PO 类**。数据库同学直接使用 `vcampus-common` 中已有的实体
`edu.seu.vcampus.common.student.entity.StudentProfile` 作为持久化载体。

本模块需要交付给数据库同学的是三样东西：**建表 SQL + 字段映射 + DAO 语义约定**。

> ⚠️ **有一处例外**：`m_real_name` 是**联表展示字段，不落库**。它由服务端在查询时按
> `userUuid` 去用户模块联查填充，写库时必须忽略。详见 §3.2。

---

## 1. 为什么不新建 VO

### 1.1 数据库结构与本模块业务模型一一对应

档案表的每一行恰好对应一个 `StudentProfile` 对象，没有多表连接、没有聚合统计、没有字段级转换。
再抽一层 VO 等于把同样的字段抄写两遍，并额外维护两份互相转换的代码，纯增加成本。

### 1.2 DAO 契约已经按实体定义好了

`StudentDao` 的方法签名（见第 2 节）返回/接收的都是 `StudentProfile`。若改为 VO，则
`StudentService`、`StudentMessageHandler`、`StudentProfileDecorator` 以及十余个测试类都要跟着改。

### 1.3 与现有模块保持一致

`User`、`BankAccount` 等实体同样直接承担数据载体职责，团队并未为它们单独定义 VO。

### 1.4 术语澄清

`StudentProfile` 严格来说是**实体（entity）**而不是 VO。VO 的定义是「无标识、不可变、按值相等」，
而 `StudentProfile` 带有主键 `m_id`。日常口语里把「数据载体」称作 VO 很常见，但提交代码时请
不要新建名为 `XxxVO` 的类。

## 2. 需要实现的 DAO 接口

### 2.1 档案仓储

接口：`vcampus-server/src/main/java/edu/seu/vcampus/server/student/StudentDao.java`
实现类请命名为 `StudentDaoJdbc`，与内存实现 `StudentDaoMemory` 同包。

| 方法 | 含义 | 语义要点 |
| --- | --- | --- |
| `StudentProfile findById(Long id)` | 按主键查一条 | 记录不存在**或已软删除**时返回 `null` |
| `StudentProfile findByUserUuid(String userUuid)` | 按账户 uuid 查本人档案 | 同上 |
| `List<StudentProfile> findAll()` | 列出全部档案 | **只返回未软删除**的；无数据返回空列表（不返回 null） |
| `List<StudentProfile> find(StudentQuery query, int offset, int limit)` | 按条件分页 | 见 §2.3 的条件对应 |
| `long count(StudentQuery query)` | 统计条数 | 与 `find` 用**同一套条件**，否则分页总数会与实际不符 |
| `boolean insert(StudentProfile profile)` | 新增 | `m_id` 为 null 时由数据库分配，**并把分配到的 id 回填到传入对象** |
| `boolean update(StudentProfile profile)` | 按主键全量更新 | `m_id` 为 null 或记录不存在时返回 `false` |
| `boolean softDelete(Long id)` | 软删除 | 仅置 `deleted = 1`，**不物理删除数据行** |

### 2.2 修改申请仓储

接口：`.../server/student/StudentModifyRequestDao.java`，实现类 `StudentModifyRequestDaoJdbc`。

| 方法 | 语义要点 |
| --- | --- |
| `boolean insert(StudentModifyRequest request)` | 主键为 null 时由数据库分配并回填 |
| `StudentModifyRequest findById(Long requestId)` | 不存在返回 null |
| `boolean update(StudentModifyRequest request)` | 审核结果回写（状态、审核人、审核时间、意见） |
| `List<StudentModifyRequest> find(ModifyRequestQuery query, int offset, int limit)` | **按提交时间倒序**，最新的在前 |
| `long count(ModifyRequestQuery query)` | 与 `find` 同一套条件 |

### 2.3 查询条件到 SQL 的对应

内存实现的过滤逻辑集中在 `StudentMatcher`，翻译成 SQL 时**逐条对照**即可：

| `StudentQuery` 条件 | SQL |
| --- | --- |
| `profileId` | `srId = ?` |
| `userUuid` | `userUuid = ?` |
| `personCategory` | `personCategory = ?` |
| `status` | `status = ?` |
| `field` | `field LIKE '%?%'`（忽略大小写） |
| `keyword` | 见下 |

`keyword` 是**多字段或**关系，且忽略大小写：

```sql
( userUuid LIKE ? OR realName LIKE ? OR field LIKE ? OR CAST(joinYear AS CHAR) LIKE ? )
```

> ⚠️ `realName` **不在本模块的表里**。若要让姓名参与数据库层过滤，需要 join 用户表；也可
> 先按本表条件查出候选集再由服务端补名过滤——**具体取舍请与模块负责人确认**，不要私自把
> 姓名字段冗余进档案表。

各条件之间是**与**的关系；单个条件内部（如 `keyword`）是**或**。

## 3. 表结构

### 3.1 建表 SQL（草案）

```sql
DROP TABLE IF EXISTS tblCampusProfile;
CREATE TABLE tblCampusProfile (
  srId            BIGINT      NOT NULL AUTO_INCREMENT COMMENT '档案主键',
  userUuid        VARCHAR(36) NOT NULL                COMMENT '所属用户 uuid',
  personCategory  VARCHAR(16) NOT NULL                COMMENT '人员类别：STUDENT/TEACHER（不含管理员）',
  joinYear        INT         NOT NULL                COMMENT '入校年份：学生=入学年份，教师=入职年份',
  status          VARCHAR(16) NOT NULL                COMMENT '在校状态：ENROLLED/SUSPENDED/WITHDRAWN/GRADUATED/RETIRED',
  field           VARCHAR(64)     NULL                COMMENT '学术方向：学生=专业，教师=研究方向',
  deleted         TINYINT(1)  NOT NULL DEFAULT 0      COMMENT '软删除标记：0 未删除，1 已删除',
  PRIMARY KEY (srId),
  KEY idx_profile_user (userUuid),
  KEY idx_profile_category (personCategory),
  KEY idx_profile_field (field)
) COMMENT='在校人员档案表（学生与教师）';

DROP TABLE IF EXISTS tblModifyRequest;
CREATE TABLE tblModifyRequest (
  mrId         BIGINT      NOT NULL AUTO_INCREMENT COMMENT '申请单主键',
  profileId    BIGINT      NOT NULL                COMMENT '目标档案主键',
  applicantUuid VARCHAR(36) NOT NULL               COMMENT '申请人账户 uuid',
  changesJson  VARCHAR(512) NOT NULL               COMMENT '变更内容，键值文本，如 status=SUSPENDED;field=计算机视觉',
  reason       VARCHAR(255)    NULL                COMMENT '申请理由',
  status       VARCHAR(16) NOT NULL                COMMENT '待审状态：PENDING/APPROVED/REJECTED',
  comment      VARCHAR(255)    NULL                COMMENT '审核意见',
  appliedAt    BIGINT      NOT NULL                COMMENT '提交时间（毫秒时间戳）',
  auditedBy    VARCHAR(36)     NULL                COMMENT '审核人账户 uuid',
  auditedAt    BIGINT          NULL                COMMENT '审核时间（毫秒时间戳）',
  PRIMARY KEY (mrId),
  KEY idx_request_profile (profileId),
  KEY idx_request_status (status),
  KEY idx_request_applied (appliedAt)
) COMMENT='档案修改申请单表';
```

> 列名风格请按团队约定统一（`sql/vCampus.sql` 里 `tblUser` 用的是 `uId`/`uName` 这类「表前缀 +
> 字段」短名，本草案为可读性未加前缀，以团队最终约定为准）。
>
> `idx_profile_field` 不是可选项：`field` 同时承载学生的专业与教师的研究方向，是「按方向找
> 师生」的检索入口（见 `docs/学籍模块接口说明.md` §7.4）。

### 3.2 Java 字段 ↔ 数据库列 映射

| `StudentProfile` 字段 | Java 类型 | 建议列名 | 列类型 | 落库 | 说明 |
| --- | --- | --- | --- | :---: | --- |
| `m_id` | `Long` | `srId` | `BIGINT AUTO_INCREMENT` | ✅ | 插入时由数据库分配并回填对象 |
| `m_user_uuid` | `String` | `userUuid` | `VARCHAR(36)` | ✅ | 引用账户 uuid |
| `m_person_category` | `PersonCategory` | `personCategory` | `VARCHAR(16)` | ✅ | 见 §3.3 |
| `m_join_year` | `int` | `joinYear` | `INT` | ✅ | 入校年份 |
| `m_status` | `CampusStatus` | `status` | `VARCHAR(16)` | ✅ | 见 §3.4 |
| `m_field` | `String` | `field` | `VARCHAR(64)` | ✅ | 学术方向 |
| `m_deleted` | `boolean` | `deleted` | `TINYINT(1)` | ✅ | 软删除标记 |
| `m_real_name` | `String` | — | — | ❌ | **联表展示字段**，查询时由服务端填充，**写入时忽略** |

### 3.3 `PersonCategory` 的取值

| 枚举值 | 显示名 |
| --- | --- |
| `STUDENT` | 学生 |
| `TEACHER` | 教师 |

**没有 `ADMIN` 取值**，这是刻意的：管理员是系统运维角色，不是校园成员，没有档案。
若数据库侧要加约束（如 `CHECK` 或枚举列），请**只允许这两个值**。

### 3.4 `CampusStatus` 的取值与落库方式

| 枚举值 | 显示名 | 学生侧读作 | 教师侧读作 |
| --- | --- | --- | --- |
| `ENROLLED` | 在校 | 在读 | 在编 |
| `SUSPENDED` | 暂离 | 休学 | 停职 |
| `WITHDRAWN` | 离校 | 退学 | 离职 |
| `GRADUATED` | 毕业 | 毕业 | — |
| `RETIRED` | 退休 | — | 退休 |

**落库方式强烈建议存「常量名」字符串（如 `ENROLLED`），不要存序号 0/1/2/3。**
枚举一旦调整顺序，序号含义整体错位，且历史数据不会有任何报错，问题极难发现。
最长常量名 `GRADUATED` 为 9 字符，`VARCHAR(16)` 留有余量。

## 4. 语义约定（实现时必须遵守）

1. **软删除**：`softDelete` 只置标记，不删数据行。所有查询（含 `findById`、`findByUserUuid`、
   `findAll`、`find`、`count`）都必须带 `deleted = 0` 条件——漏掉一处就会让已注销的档案重新出现。
2. **id 回填**：`insert` 成功后必须把数据库分配的 id 写回传入对象，否则调用方拿不到主键，
   后续的 `update` / 变更申请都会失败。
3. **`find` 与 `count` 条件一致**：两处条件必须来自同一份判断，否则分页总条数会与实际情况不符
   （这类缺陷在数据量小时不易发现）。
4. **排序稳定**：`StudentModifyRequestDao.find` 必须按 `appliedAt DESC`；时间戳相同的记录用
   主键做次级排序，避免分页时同一条记录重复出现或漏掉。
5. **不改枚举顺序**：`PersonCategory` / `CampusStatus` 的取值顺序即协议约定，只允许在末尾追加。
6. **忽略 `m_real_name`**：见 §3.2 的例外说明。

---

## 5. 测试要求

JDBC 实现应与内存实现**共用同一套契约测试**。建议把现有 `StudentDaoMemoryTest` 的断言
抽成可复用的用例集合，对两种实现各跑一遍——这样能保证「换实现不改行为」。

重点覆盖：

- 软删除后 `findById` / `findAll` / `count` 都不再返回该记录；
- `insert` 回填 id；
- 分页边界：`offset` 越界返回空列表、`limit` 非正返回空列表；
- 条件组合（与/或）与 SQL 结果一致；
- 空结果返回空列表而不是 null。
