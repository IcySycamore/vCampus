## 1. 模块范围

学籍模块负责**在校人员档案**的查询、登记、修改申请、审核、注销与状态变更。档案覆盖**学生与教师两类人员**。

| 项目 | 内容 |
| --- | --- |
| 命令码号段 | 200 – 299 |
| 处理器 | `StudentMessageHandler`（权限准入） + `StudentCommandExecutor` / `StudentWriteExecutor`（业务执行） |
| 服务层 | `StudentService`、`StudentModifyFlow`（审核流）、`StudentProfileDecorator`（姓名联查）、`StudentChangeCodec`（变更编解码） |
| 数据访问 | `StudentDao`、`StudentModifyRequestDao`（接口） + `StudentDaoMemory`、`StudentModifyRequestDaoMemory`（内存实现，占位） |
| 服务端包 | `edu.seu.vcampus.server.student` |
| 客户端包 | `edu.seu.vcampus.client.student`（`StudentService` / `StudentModule`）、`edu.seu.vcampus.client.api`（`ApiException`） |
| 公共数据载体 | `StudentProfile`、`PersonCategory`、`CampusStatus`、`PageResponse`、`Command`、`StatusCode` |
| 界面入口 | 侧栏「个人信息」（`PageNames.STUDENT`） |

### 1.1 只维护师生，不维护管理员

这是本模块的一条硬约束：**管理员是系统运维角色，不是校园成员，没有学籍或职工档案**。

落地方式是**类型层面排除**而不是运行时判断——`PersonCategory` 枚举只有 `STUDENT` 与 `TEACHER` 两个取值，**根本没有「管理员」这个取值**，因此「给管理员建一条档案」这件事在代码里无法表达。这比在每个入口写「如果角色是管理员则拒绝」可靠得多，后者只要漏写一处就是漏洞。

### 1.2 与用户模块的分工

| 数据 | 归属 | 说明 |
| --- | --- | --- |
| 登录名、密码、角色、**姓名** | 用户模块 | `User` / `UserRepository` |
| 人员类别、入校年份、在校状态、专业/研究方向 | 本模块 | `StudentProfile` |
| 两者的关联 | 本模块存 `userUuid` | 只引用，不冗余 |

查询档案时服务端会按 `userUuid` **联查用户模块把姓名填进 `realName`**（见 §4.1），所以客户端**不需要**为了显示姓名再发一次请求。

## 2. 通用约定

### 2.1 通信方式

- 传输层：**TCP 长连接**；
- 序列化：**Java 对象序列化**（`ObjectOutputStream` / `ObjectInputStream`），**不是 JSON、不是 HTTP**；
- 每条消息**独立完整**序列化：发送方在 `writeObject` 前会 `reset()` 清空引用缓存。自行实现收发时务必照做，否则第二次发送同一个可变对象时，对端只会拿到第一次的旧值（back-reference 陷阱）；
- 交互单元：客户端与服务端互发 `edu.seu.vcampus.common.message.Message` 对象。

### 2.2 消息信封 `Message`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `uid` | `Long` | 请求唯一标识，响应原样回填，客户端据此关联请求与响应 |
| `command` | `int` | 命令码，见第 3 节 |
| `statusCode` | `String` | 状态码，见 2.4；**请求中留空，仅响应使用** |
| `data` | `Object` | 业务数据，类型随命令码而定，见第 4 节 |
| `sender` | `String` | 发送方标识（预留） |
| `token` | `String` | 会话令牌，**除登录外所有请求必须携带** |

### 2.3 认证与鉴权

- 客户端登录成功后由 `SessionManager` 签发 `token`；之后每个请求在 `token` 字段带上该令牌；
- 令牌 30 分钟**滑动过期**，每次有效请求自动续期；
- `token` 缺失 / 无效 / 过期 → `401`，客户端应引导用户重新登录；
- `token` 有效但**能力不足** → `403`；
- 权限判定读 `Permissions` 矩阵（`common.user.entity`），处理器只做「命令码 → 能力」的映射，规则集中在矩阵里。

**角色（`Role`）与人员类别（`PersonCategory`）是两件事，不要混用**：

| | `Role` | `PersonCategory` |
| --- | --- | --- |
| 用途 | 登录与权限划分 | 人员档案划分 |
| 取值 | 学生 / 教师 / **管理员** | 学生 / 教师（**无管理员**） |

### 2.4 状态码（`StatusCode`）

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `SUCCESS` | `200` | 成功 |
| `BAD_REQUEST` | `400` | 参数错误（含类型不匹配、未知命令码） |
| `UNAUTHORIZED` | `401` | 未登录或会话失效 |
| `FORBIDDEN` | `403` | 无权限执行该操作 |
| `NOT_FOUND` | `404` | 目标档案不存在 |
| `INTERNAL_ERROR` | `500` | 服务器内部错误 |

### 2.5 三轨查询与「不静默降级」

同一个 201 命令按调用者身份分三条轨：

| 轨 | 调用者 | 行为 |
| --- | --- | --- |
| 我的轨 | 任何人 | 请求不带目标标识 → 服务端按会话 uuid 返回**本人**档案 |
| 全量轨 | 具备 `STUDENT_VIEW_ALL`（教师 / 管理员） | 按主键或条件查任意人 |
| 受限轨 | — | 无全量能力者按主键查**他人** → **403** |

**关键点**：越权时回 403，**不会**悄悄降级成「只返回你自己的」。静默降级会让界面拿到一条看起来正常的记录，掩盖真实的权限问题。

## 3. 命令码总表

| 命令码 | 常量名 | UI 操作 | 请求 `data` | 响应 `data` | 权限 |
| --- | --- | --- | --- | --- | --- |
| 201 | `STUDENT_QUERY` | 查询档案 | `StudentQuery`（或兼容的 `Long`） | `StudentProfile` | 登录即可（范围见 §2.5） |
| 202 | `STUDENT_MODIFY_APPLY` | 提交修改申请 | `StudentModifyRequest`（dto） | — | 学生 |
| 203 | `STUDENT_MODIFY_AUDIT` | 审核修改申请 | `ModifyAuditRequest` | — | 教师 / 管理员 |
| 204 | `STUDENT_REGISTER` | 登记档案 | `StudentProfile` | — | 管理员 |
| 205 | `STUDENT_DELETE` | 注销档案 | `StudentDeleteRequest`（兼容 `Long`） | — | 管理员 |
| 206 | `STUDENT_CHANGE_STATUS` | 修改在校状态 | `StudentStatusRequest`（兼容 `StudentProfile`） | — | 教师 / 管理员 |
| 207 | `STUDENT_MODIFY_LIST` | 待审申请列表 | `ModifyRequestQuery` | `PageResponse<StudentModifyRequest>` | 教师 / 管理员 |
| 208 | `STUDENT_LIST` | 档案列表 | `StudentQuery` | `PageResponse<StudentProfile>` | 教师 / 管理员 |

**兼容说明**：201 / 205 / 206 同时接受「旧版简单类型」与「新版 DTO」两种请求体，便于灰度期旧客户端继续可用。

**209 – 299** 为保留号段，未登记的命令码由分发器统一回 `400`。

## 4. 各命令详情

### 4.1 查询档案（201 `STUDENT_QUERY`）

- **请求 `data`**：`StudentQuery`；`m_profile_id` 为空表示「查我自己」。也接受裸 `Long`（旧版）。
- **响应 `data`**：`StudentProfile`。
- **状态码**：`200` 成功；`404` 无档案；`403` 查他人但无 `STUDENT_VIEW_ALL`；`400` 参数类型不正确。

**响应里的 `realName` 是服务端联查填好的**：学籍表只存 `userUuid`，姓名归用户模块。若让客户端自己再查一次，列表页就会退化成 N+1 次请求。因此服务端在返回档案前按 uuid 把姓名填进 `realName`（`StudentProfileDecorator`）。

该字段的取值规则：
1. 用户模块登记了姓名 → 用姓名；
2. 没登记姓名（如管理员账号）→ 用**登录名**顶上；
3. 账户查不到（已注销）→ 用 **uuid** 顶上。

**三种情况都保证非空**，所以界面拿到就能直接贴，不需要「姓名为空则显示别的」这种回退分支。

> ⚠️ `realName` 是**联表展示字段，不落库**。写库时忽略它；接 JDBC 实现时不要把它写进学籍表。

### 4.2 提交修改申请（202 `STUDENT_MODIFY_APPLY`）

- **请求 `data`**：`StudentModifyRequest`（dto）—— `profileId`、`changes`（`Map<String,String>`）、`reason`。
- **状态码**：`200` 成功；`400` 参数为空 / 目标档案不存在 / 没有任何可修改的字段。

**语义要点**：202 **只落一条待审申请，不改档案**。审核通过（203）才会真正生效——这正是「学生申请 → 教务审核」的体现，提交即生效就失去了审核的意义。

**可修改字段白名单**（`StudentChangeCodec`）：

| 字段名 | 含义 | 取值 |
| --- | --- | --- |
| `joinYear` | 入校年份（学生入学 / 教师入职） | 十进制整数 |
| `status` | 在校状态 | 枚举名，如 `SUSPENDED` |
| `field` | 学术方向（学生专业 / 教师研究方向） | 文本 |

白名单之外的字段（例如 `userUuid`）会被**静默丢弃**；若全是非法字段则整单拒绝。编码与解码两处都校验白名单，所以绕过界面直接构造请求也改不了不该改的字段。

### 4.3 审核修改申请（203 `STUDENT_MODIFY_AUDIT`）

- **请求 `data`**：`ModifyAuditRequest` —— `requestId`、`approved`、`comment`。
- **状态码**：`200` 成功；`400` 参数为空 / 申请不存在 / **已被审核过**。
- **审核人**取会话 uuid，**不放在请求体里**，客户端伪造不了审核人。

通过时把申请中的变更应用到档案；驳回时档案保持原样，但仍记录审核人、审核时间与意见（留痕）。**同一条申请不能审核两次**，否则变更会被反复应用。

### 4.4 登记档案（204 `STUDENT_REGISTER`）

- **请求 `data`**：`StudentProfile`（`id` 留空，服务端分配）；`personCategory` 决定建的是学生还是教师档案。
- **状态码**：`200` 成功；`400` 记录非法（`userUuid` 为空）。
- **权限**：管理员。

### 4.5 注销档案（205 `STUDENT_DELETE`）

- **请求 `data`**：`StudentDeleteRequest`（`profileId`）；也接受裸 `Long`。
- **状态码**：`200` 成功；`404` 记录不存在；`400` 参数为空。
- **软删除**：仅置 `deleted = true`，记录仍保留。选课、成绩、借阅等模块对 uuid 的引用不会变成悬空指针。

### 4.6 修改在校状态（206 `STUDENT_CHANGE_STATUS`）

- **请求 `data`**：`StudentStatusRequest`（`profileId` + `status`）；也接受只填 `id` + `status` 的 `StudentProfile`。
- **状态码**：`200` 成功；`404` 记录不存在或参数非法；`400` 参数为空。
- **权限**：教师 / 管理员。

### 4.7 待审申请列表（207 `STUDENT_MODIFY_LIST`）

- **请求 `data`**：`ModifyRequestQuery` —— `status?`、`profileId?`、分页。
- **响应 `data`**：`PageResponse<StudentModifyRequest>`，**按提交时间倒序**（最新的排最前，教务先看到新提交的）。
- **权限**：教师 / 管理员。

### 4.8 档案列表（208 `STUDENT_LIST`）

- **请求 `data`**：`StudentQuery` —— `keyword?`、`status?`、`personCategory?`、`field?`、分页。
- **响应 `data`**：`PageResponse<StudentProfile>`，每条都带 `realName`。
- **权限**：教师 / 管理员（要求 `STUDENT_VIEW_ALL`）。

**关键字的匹配范围**：姓名、账户 uuid、学术方向、入校年份。把**专业与研究方向**一并纳入同一个关键字，是因为界面只有一个搜索框——用户不会先去区分「这是姓名还是专业」；同时这也让「按方向找师生」成为可能：查「计算机」既命中该专业的学生，也命中该方向的教师（见 §7.4）。

**分页**：页码从 1 开始；每页默认 20 条，服务端会把超过 100 的请求值截断到 100，防止一次拉爆数据。

## 5. 权限矩阵

| 命令码 | 学生 | 教师 | 管理员 |
| --- | :---: | :---: | :---: |
| 201 查询档案 | ✅ 仅本人 | ✅ 全部 | ✅ 全部 |
| 202 提交修改申请 | ✅ | ❌ | ❌ |
| 203 审核修改申请 | ❌ | ✅ | ✅ |
| 204 登记档案 | ❌ | ❌ | ✅ |
| 205 注销档案 | ❌ | ❌ | ✅ |
| 206 修改在校状态 | ❌ | ✅ | ✅ |
| 207 待审申请列表 | ❌ | ✅ | ✅ |
| 208 档案列表 | ❌ | ✅ | ✅ |

矩阵定义在 `common.user.entity.Permissions`（`Capability` × `Role`），客户端用它决定控件可见性，服务端用它准入。**两侧读同一张表**，界面显示与后端判定不会打架。

管理员保留学籍管理能力，是因为它要能代教务操作；被排除的是「管理员有档案」这件事本身（§1.1）。

## 6. 客户端对接

### 6.1 推荐方式：`client.student.StudentService`

```java
StudentService student = StudentModule.register(dispatcher, userService.getSession());

StudentProfile me = student.queryMyProfile();          // 201，无需传身份
PageResponse<StudentProfile> all = student.listStudents(query);   // 208
student.applyModification(request);                    // 202
student.auditModification("42", true, "同意");          // 203
```

约定：

1. **同步阻塞**：方法返回实体或分页结果，拿到即渲染；
2. **失败抛 `ApiException`**（非受检）：界面不需要 try/catch，也不必接触 `Message` / 命令码 / 分发器；
3. **方法名是业务动作**：`applyModification` 而不是 `sendModifyCommand`；
4. **身份由服务端解析**：查自己的档案不传 uuid，客户端伪造不了身份。

### 6.2 自行组消息时

1. 发起请求前先设置 `token`；`uid` 用唯一值，收到响应后按 `uid` 匹配；
2. 统一在收包回调中**先判 `statusCode`**：`401` → 跳登录；`403` → 提示无权限；`404` → 提示不存在；`400` → 提示参数错误；`200` → 再解析 `data`；
3. 解析 `data` 前做 `instanceof` 判断，不要盲目强转。

## 7. 数据模型

### 7.1 `StudentProfile`

| 字段 | 类型 | 落库 | 说明 |
| --- | --- | :---: | --- |
| `m_id` | `Long` | ✅ | 主键，服务端分配 |
| `m_user_uuid` | `String` | ✅ | 关联用户模块的 uuid（仅引用，不冗余用户信息） |
| `m_person_category` | `PersonCategory` | ✅ | 人员类别：学生 / 教师 |
| `m_join_year` | `int` | ✅ | 入校年份：学生=入学年份，教师=入职年份 |
| `m_status` | `CampusStatus` | ✅ | 在校状态 |
| `m_field` | `String` | ✅ | 学术方向：学生=专业，教师=研究方向 |
| `m_real_name` | `String` | ❌ | **联表展示字段**，查询时由服务端填充，写库忽略 |
| `m_deleted` | `boolean` | ✅ | 软删除标记 |

### 7.2 `PersonCategory`

| 枚举值 | 显示名 | 说明 |
| --- | --- | --- |
| `STUDENT` | 学生 | 在册 |
| `TEACHER` | 教师 | 在编 |

**没有 `ADMIN` 取值**——见 §1.1。

### 7.3 `CampusStatus`

| 枚举值 | 显示名 | 学生侧读作 | 教师侧读作 |
| --- | --- | --- | --- |
| `ENROLLED` | 在校 | 在读 | 在编 |
| `SUSPENDED` | 暂离 | 休学 | 停职 |
| `WITHDRAWN` | 离校 | 退学 | 离职 |
| `GRADUATED` | 毕业 | 毕业 | — |
| `RETIRED` | 退休 | — | 退休 |

> 之所以叫「在校状态」而不是「学籍状态」：档案同时承载师生两类人员，状态字段两边共用，取值是同一套，显示名取两边都能接受的中性表述。

### 7.4 专业与研究方向的对应

学生的**专业**与教师的**研究方向**是**同一个字段 `m_field` 的两种叫法**：

- 服务端只维护一个字段、一个索引；
- 界面按 `personCategory` 切换标签——学生看到「专业」，教师看到「研究方向」；
- 检索时两边一起命中：查「计算机」既返回该专业的学生，也返回该方向的教师。

这样处理的理由：教师的招生方向与学生的专业本就是同一套词汇，分开存反而要在查询时查两次再合并。

> 如果需要的是「学生 ↔ 导师」的**配对关系**（谁指导谁），那是另一个功能，需要单独的关系表，不在本字段的职责范围内。
